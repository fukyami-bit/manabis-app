# 来校管理システム 要件定義書

マナビス新松戸校／2026-10-04 作成

---

## 1. 背景と目的

### 1.1 解決する課題

平日の開館は 14:00–21:45 だが、アルバイトスタッフ（以下AA）の出勤は早くても 17:00 である。
来校登録はほぼAAが担当しているため、**14:00–17:00 に来校した生徒の登録が未処理のまま溜まり、
AAは出勤直後にその消化へ時間を取られる**。これが現場で最も負担となっている。

職員は 14:00–17:00 も在席しているが面談等に対応しており、登録作業に回せない。

### 1.2 課題の構造

現行の来校登録は、生徒が紙の「来校カード」に記入した内容を、スタッフがシステムへ打ち直す
**二度手間**になっている。

```
① 生徒が来校カードに記入（氏名・ブース番号・次回来校予定日）
② カードをスタッフに渡す
③ スタッフが受講ファイルを渡す
④ スタッフがカードを見てシステムへ入力     ← 17:00 に溜まる作業
```

登録作業が来校イベントから「時刻」も「担当者」も切り離されているため、次の2点が同時に起きている。

1. 労働が 17:00 に集中する
2. 記録された来校時刻が実態と合わない（後述 2.3）

### 1.3 目的

生徒自身のスマートフォンからQRコード経由でフォームに入力させ、**その送信をもって来校登録を完了**
させる。スタッフの転記作業を無くし、同時に正確な来校時刻を記録する。

## 2. 現行システムの調査結果

対象ファイル: 来校管理用 Excel マクロ有効ブック（.xlsm、4シート、VBA 489行）

アラート数式（I列）

```
=IF(C5="","",IF(G5<>"","",IF(J5<>"","",IF(F5="","",IF($E$2>MOD(F5,1)+$H$2,"要電話","")))))
```

来校予定時刻から1時間を過ぎても未登録なら「要電話」を表示する。状況は
**来校済／遅刻／欠席／無断欠席** の4種で、条件付き書式により色分けされる。

### 2.5 検出した問題点

**A. データ構造**

| # | 問題 | 根拠 |
|---|---|---|
| A-1 | **行番号固定リンクによる人物ズレ**。予約を貼り直すと手入力のG/H/J列が取り残され、別の生徒に紐づく | 調査時点で **43行で発生中**（10/04の予約が表示される行に10/03の来校記録が残存）。さらに8行は氏名が空のまま来校時間だけ残存 |
| A-2 | **来校履歴が残らない**。日次でクリアするため前日以前のデータが存在せず、最終来校日・来校頻度を算出できない | `本日の来校情報をクリア` が G/H/J 列を消去 |
| A-3 | 容量が固定（予約300件・予約なし50件） | 行を事前確保する構造 |
| A-4 | 退校時刻を記録する列がない。滞在時間が取れず、ブースの空き状況も把握できない | 列構成に該当列なし |
| A-5 | `未予約貼り付け` シートがどの数式からも参照されていない（参照0件）ため、目視で突合している | 全シートの数式を走査 |

**B. 運用**

| # | 問題 | 根拠 |
|---|---|---|
| B-1 | **毎朝のクリア忘れが業務停止に直結**。`来校登録` はG列が空の行しか検索対象にしないため、クリアを忘れると当日の生徒を登録できない。アラートもG/J列が埋まっているため発火しない。警告機構は存在しない | A-1と同一事象 |
| B-2 | 本部システムから3シートへ日次で手貼りしている | 運用ヒアリング |
| B-3 | 現在時刻が `NOW()` のため再計算時のみ更新。アラート確認に `再計算` ボタンが必要 | E2セル |
| B-4 | 受付入力が InputBox の連打。氏名を漢字で部分入力し候補番号を数字で入力する。名簿にカナがあるがマクロは氏名列のみ検索 | Module4 |
| B-5 | 単一ファイル・単一端末のため同時編集できない | ファイル形式 |

**C. セキュリティ**

| # | 問題 | 根拠 |
|---|---|---|
| C-1 | 保護者氏名・住所・電話番号・生年月日を含むファイルを受付で常時開いている。来校管理に必要なのは生徒番号・氏名・学年・高校名のみ | 名簿18列の内容 |
| C-2 | シート保護は `来校管理` のみ。個人情報を含む `生徒名簿貼り付け` は無保護 | 各シートの protection 設定 |

**D. 保守性**

| # | 問題 |
|---|---|
| D-1 | 旧マクロが3系統残存し機能が重複している（D-1は改修時の修正漏れリスク） |
| D-2 | 行番号 5／304／306／355／1000 が各プロシージャにハードコードされている |

### 2.6 データ品質上の欠陥

マクロは来校時刻に `Now`（**入力した瞬間の時刻**）を書き込む。

```vb
ws.Cells(targetRow, "G").Value = Now
```

14:30に来校した生徒を17:20に登録すれば、来校時刻は17:20として記録される。さらに `生徒登録` は
予約時刻＋1時間を超えて登録されると自動で「遅刻」に変更する。

```vb
If nowTimeOfDay > resTimeOfDay + wsK.Range("H2").Value Then
    finalStatus = "遅刻"
```

このため**時間通りに来校した生徒が、登録の遅れによって「遅刻」と記録される**。
調査対象日は遅刻16件（21%）だが、予約データが翌日分に差し替わっているため誤判定の件数は確定できない。

## 3. 新システムの業務フロー

```
【現行】
  ① 生徒が来校カードに記入（氏名・ブース番号・次回来校予定日）
  ② カードをスタッフに渡す
  ③ スタッフが受講ファイルを渡す
  ④ スタッフがシステムへ入力                    ← 廃止対象

【新】
  ① 生徒がQRコードを読み取り、フォームに入力して送信
       └─ この時点で来校登録が完了（送信時刻＝来校時刻）
  ② スタッフが来校一覧を見て受講ファイルを渡し、配布済みにチェック
       └─ 受付が無人の場合は生徒は先に着席し、スタッフが後から届ける
  ③ 自習者の次回来校予定を本部システムへ入力
```

来校カードは廃止する。カードが担っていた「この生徒が来た」という伝達は、
スタッフ画面のリアルタイム来校一覧が引き継ぐ。

## 4. 機能要件

### 4.1 生徒用フォーム（スマートフォン／QRコードから起動）

| # | 項目 | 要件 |
|---|---|---|
| F-1 | マナビス生番号 | 6桁を入力。名簿と照合し氏名を表示して「〜さんで合っていますか？」と本人確認させる。該当なしの場合はエラー表示 |
| F-2 | 今日の目的 | **受講／自習** を選択。以降の項目を分岐させる |
| F-3 | ブース番号 | 数値入力。範囲チェック（1–2／3–70／71–90／101–120）。範囲外は受け付けない |
| F-4 | 次回来校予定日 | **自習を選択した場合のみ必須**。受講の場合は不要（受講ブースのPCで生徒自身が次回予約を取れるため） |
| F-5 | 送信 | 送信時刻を来校時刻として記録する |
| F-6 | 二重送信の防止 | 同一生徒が当日すでに送信済みの場合は警告を表示する |

**氏名リストから選択させる方式は採用しない。** 152名の氏名が全生徒に開示されることになるため。

生徒番号の誤入力による他生徒の氏名表示リスクは実用上無視できる。

- 6桁、152名が幅60,527の中に散在（実在番号は全体の0.3%）
- 1文字の打ち間違い8,208通りのうち、別の実在生徒に当たるのは**18通り＝0.2%**
- 99.8%は「該当なし」で弾かれるため、入力ミス検知としても機能する

### 4.2 スタッフ画面（受付のPC／タブレット）

| # | 機能 | 要件 |
|---|---|---|
| S-1 | リアルタイム来校一覧 | 送信順に表示。氏名・来校時刻・目的・ブース番号・予約有無・状況を表示。**来校カード廃止の代替となるため必須機能** |
| S-2 | ファイル配布管理 | 全来校者が対象。未配布／配布済みを切り替える。未配布者をブース番号付きで一覧表示し、配達先が分かるようにする |
| S-3 | 予約との自動突合 | 生徒番号をキーに予約データと突合し、予約あり／なしを判定する |
| S-4 | 遅刻判定 | フォーム送信時刻（正確な来校時刻）と予約時刻を比較して判定する |
| S-5 | 要電話アラート | 予約時刻から基準時間（既定1時間）を過ぎても未来校の生徒を表示する。基準時間は変更可能とする |
| S-6 | 欠席・無断欠席の登録 | 来校しなかった生徒はフォームに現れないため、スタッフが登録する |
| S-7 | 次回来校予定の一覧 | 自習者が入力した次回来校予定日を一覧表示する。本部システムへの入力作業に使う |
| S-8 | 代理入力 | スマートフォンを持たない生徒の受付用。校舎スマートフォンでの本人入力が可能なため低頻度の想定 |
| S-9 | 本部データの取り込み | 生徒名簿・来校予約を取り込む |

### 4.3 データ要件

| # | 要件 |
|---|---|
| D-1 | 来校ログは**追記型**とする。日次クリアを行わない。これにより A-2（履歴が残らない）と B-1（クリア忘れ）が構造的に解消される |
| D-2 | 生徒の突合キーは**マナビス生番号**とする。行番号による参照を廃止し、A-1（人物ズレ）を解消する |
| D-3 | 来校ログ1件の項目: 生徒番号／来校日時／目的（受講・自習）／ブース番号／次回来校予定日／ファイル配布済みフラグ／状況／登録経路（生徒本人・代理） |
| D-4 | 件数上限を設けない（A-3の解消） |
| D-5 | `未予約貼り付け` シートは廃止する。「予約を持たない在籍者」は名簿と予約データの差分として算出できる（A-5の解消） |

### 4.4 本部システム連携

| # | 要件 |
|---|---|
| H-1 | 生徒名簿・来校予約のエクスポートを取り込む運用は現行どおり継続する（本部システム側の仕様に依存するため自動化は対象外） |
| H-2 | 自習者の次回来校予定は、S-7の一覧を見てスタッフが本部システムへ入力する（本部システムへの書き込みAPIが無いため自動化は対象外） |

## 5. 非機能要件

| # | 分類 | 要件 |
|---|---|---|
| N-1 | リアルタイム性 | フォーム送信からスタッフ画面への反映は数秒以内。S-1がファイル配布の前提となるため |
| N-2 | 同時利用 | 生徒の同時送信と、スタッフ複数端末からの閲覧・更新を許容する |
| N-3 | 個人情報の最小化 | 来校管理側に保持するのは生徒番号・氏名・氏名カナ・学年・高校名に限る。保護者氏名・住所・生年月日は保持しない（C-1の解消）。電話番号については 7. 未決事項 を参照 |
| N-4 | フォールバック | 生徒のスマートフォンが使えない場合は校舎スマートフォンで本人が入力する。それも不可の場合はS-8の代理入力を使う |
| N-5 | 可用性 | 通信障害時にフォームが開かない場合に備え、受付で記録して後から入力できる手段を残す |
| N-6 | 入力時間 | 生徒のフォーム入力は30秒以内で完了できる操作数とする |

## 6. 実装方式

### 6.1 要件から導かれる制約

| 要件 | 排除される選択肢 |
|---|---|
| F-1（生徒番号から氏名を引いて確認表示） | **Googleフォームは使用できない**。静的フォームでは名簿への動的照合ができない。自作Webフォームが必須 |
| S-1（リアルタイム来校一覧） | **来校管理をExcelファイルのまま維持できない**。フォームのデータを手動でCSV取り込みすることになり、廃止したはずの転記作業が1日に何度も復活する |

### 6.2 構成

```
[生徒のスマホ] ──QR──> 生徒用Webフォーム
                              │ 送信
                              ▼
                     サーバ側（来校ログ・追記型）
                      ├─ 生徒名簿（本部エクスポート）
                      └─ 来校予約（本部エクスポート）
                              │
                              ▼
              [受付PC／タブレット] スタッフ画面
```

### 6.3 既存資産の流用

本リポジトリの `index.html` には、本構成に必要な実装が既に存在する。

| 既存実装 | 流用先 |
|---|---|
| サーバエンドポイントへの POST ＋トークン認証（`syncCall()`） | 来校ログの読み書き |
| SheetJS によるExcel読み込み | H-1（本部エクスポートの取り込み） |
| 2モード切替のUI構造（PC向け／iPhone向け） | スタッフ画面を第3のモードとして追加 |

## 7. 未決事項

| # | 項目 | 判断が必要な理由 |
|---|---|---|
| U-1 | QRコードの設置場所（入口／カウンター） | 生徒の導線と、ブース選択のタイミングに影響する |
| U-2 | 電話番号を来校管理側に保持するか | S-5の要電話アラートからその場で発信するなら必要。保持すればN-3の個人情報最小化と相反する |
| U-3 | 退校打刻を導入するか | 導入すれば滞在時間とブースの空き可視化が可能になるが、生徒の手間が倍になり忘れられるリスクが高い。**第1段階では対象外とする** |
| U-4 | 移行方法（並行運用期間を置くか、一斉切替か） | 来校カードを廃止するため、フォームが動かない場合の影響が大きい |
| U-5 | スタッフ画面を既存 `index.html` に統合するか、独立させるか | 既存の面談機能との関係 |

---

## 8. 対象外（第1段階では実装しない）

| 項目 | 理由 |
|---|---|
| 退校打刻・滞在時間の記録 | U-3のとおり生徒の負担が大きい |
| 空きブースのリアルタイム表示 | 退校を記録しない限り空き状況を把握できない。生徒が自分の目で空席を確認する現行方式を維持する |
| ブース番号の重複チェック | 退校を記録しないため「重複」と「入れ替わりによる再利用」を区別できない（実測で同一ブースの再使用が8件）。範囲チェックのみ実施する |
| 本部システムへの自動書き込み | H-2のとおりAPIが無い |
| 本部エクスポートの自動取得 | H-1のとおり本部システム側の仕様に依存する |
| 来校履歴を使った分析機能（最終来校日・来校頻度・未来校者の抽出） | D-1により履歴は蓄積されるため、第2段階で追加可能 |

## 9. 期待効果

| 課題 | 効果 |
|---|---|
| 14:00–17:00の登録滞留 | **解消**。生徒の送信をもって登録が完了するため、スタッフの転記作業が無くなる |
| 来校時刻の不正確さ（2.6） | **解消**。送信時刻が実際の来校時刻となる |
